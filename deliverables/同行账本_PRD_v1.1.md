## 1. 产品摘要与已确定方向

产品让一组朋友在弱网、没有公网、甚至无线连接完全不可用时仍能记账。每个成员保存本地副本，连接出现时交换签名事件，而不是依靠服务器上的唯一数据库。

产品长期目标与当前规则如下。目标描述不表示 v0.2.1 已提供对应适配；本版可用范围见第 26 节：

- 支持 Android 和 iOS，同一群组使用相同业务规则与数据协议。
- 支持多币种、多付款人、多参与人；记录人、付款人、承担人相互独立。
- 支持按币种或合并币种结算，以及保留一对一关系或优化支付次数。
- 所有人可以查看同一版本的结算快照；离线实时预览须标明数据范围。
- 管理员或获授权成员可以修改别人创建的账单，但必须保留修订与签名历史。
- 本地查看、记账、修改和试算不依赖公网、在线汇率或链节点。
- 局域网是主同步通道；WebDAV 解决非同时在线成员之间的加密留存问题。
- 支持导出加密同步文件，由系统分享、AirDrop、兼容的 Quick Share/小米互传等搬运。
- 支持完全无无线连接时的面对面光学传输；动态二维码优先于自研彩色光学通信。
- 数据图片和编码文本可以作为同一同步包的附加载体，不替代原始文件可靠通道。

**核心原则：传输与业务解耦。**任意通道收到的数据，均经过同一套解密、签名、权限、依赖和财务校验。传输成功不代表已入账，已入账不代表所有成员同意，发布结算方案不代表钱已支付。

P0/P1/P2 表示需求优先级，不是“是否已经完成”的标签。原优先级保留，不因当前缺实现而降级。性能数字除特别说明外都是目标或历史样本估算，不能当作实测。

## 2. 背景、问题与目标

### 2.1 典型问题

旅行中可能没有移动数据、酒店 Wi-Fi 无公网、不同成员只有间歇联网机会。多人垫付、多币种消费、部分成员参加活动，使简单的表格分摊和人工对账容易出错。管理员纠错、成员同时修改、还款到账确认及汇率变化又会引入状态歧义。

个人开发者还面临持续服务器费用、后端运维、账号体系、隐私和服务关闭后的数据可用性问题。产品应降低对业务服务器的依赖，但不能把使用现成 WebDAV、推送或系统分享服务描述为完全不存在服务器。

### 2.2 产品目标

- 断网时可完整进行本地业务操作，并明确提示未同步或待确认状态。
- 同一已验证事件集合、相同政策与相同算法版本产生相同结果。
- 账单可审计，授权修订不抹去历史；财务字段冲突不静默覆盖。
- 明确区分消费承担、垫付、实际还款、币种重分类和债务重组。
- 既支持原始一对一关系，也支持减少转账次数，且不虚称最优。
- 各通道可替换；留存节点停服不导致本机账本不可用。
- 跨平台体验尽可能统一，同时诚实反映 iOS/Android 后台限制。

### 2.3 非目标

- 不托管资金，不代用户执行银行转账，不保证消费或到账事实真实。
- 不要求钱包、代币、Gas 或公共区块链；链上锚定不进入 MVP。
- 不保证断网成员瞬时获知新记录、权限撤销或最新结算。
- 不提供恶意群主场景下的拜占庭共识，也不承诺服务器无法扣留文件。
- 不保证所有小米/Android 机型都能直接使用 AirDrop。
- 不将聊天截图、消费图片 OCR 或图片识别结果自动视为可信账单。
- 不默认进行跨群组资金抵扣、跨群合并结算或自动实时汇率重估。

## 3. 用户、角色与使用场景

| 场景 | 用户需要 | 产品行为 |
| --- | --- | --- |
| 山区或境外无移动数据 | 离线录入餐费、门票 | 本地立即保存；使用已有或手工冻结汇率；不等联网 |
| 大家住同一酒店 | 同步当天账目 | 在允许客户端互通的局域网交换缺失事件；无公网也可 |
| 成员错峰上线 | 获取别人此前的修改 | 可访问的 WebDAV 留存密文；上线后拉取并验证 |
| A 录入、B/C 付款 | 多付款人、不同承担人 | 分别记录记录人、垫付明细、承担明细 |
| 财务负责人发现错误 | 修改别人账单 | 提交授权新修订，展示原因与修改前后差异 |
| 两人离线同时改金额 | 防止覆盖或拼错金额 | 保存两个财务修订，显示冲突，授权人员明确解决 |
| 多币种结算 | 选择原币或一种结算币种 | 预览不同模式；正式方案冻结汇率与债务范围 |
| 不想转很多次钱 | 简化债务 | 优化净余额支付；共同确认后明确重组结算义务 |
| 没有可用无线连接 | 面对面同步几笔账 | 收发动态二维码，恢复并验签后导入 |
| 系统互传可用 | 快速交换整包更新 | 导出文件，使用系统分享，接收后导入去重 |

角色：群主、财务编辑、普通成员、只读成员。没有安装 App 的参与人可以作为“账务参与人”录入，但不得虚构其本人数字签名或自动认为其同意结算。

推荐使用规模为 2–20 人；协议设计预留更大群组，但不以此承诺所有规模都能快速求得最少支付次数。

## 5. 产品架构与边界

### 5.1 推荐架构

- 共享界面：已采用 Flutter；当前只有 Android 工程和 arm64 APK，iOS 仍未实现。
- 共享业务核心：已采用 Rust + C ABI FFI，Flutter 经后台 Isolate 调用；现有测试不能替代跨平台验收。
- 本地存储：SQLite 保存事件、工作区元数据、签名身份及出箱；安装级目录登记多个独立账本文件。事件投影按需计算，不把当前全部状态原子性视为已验收。
- 局域网连接：基于可替换的直连适配层；采用 iroh 时显式配置本地发现/直接地址。
- 系统适配：摄像头、分享/导入、密钥存储、网络权限和生命周期分别接入 Android/iOS。
- 留存服务：WebDAV 等只负责存取密文，不决定权限、当前账单或结算。

技术选项不是已经完成的 SDK 接入。iroh 有 Swift/Kotlin 支持，但 Android 原生构件、Flutter 桥接、最低系统和离线发现需要 PoC；不能按“添加依赖即生产可用”排期。

### 5.2 三层数据

1. 不可变业务事件：签名、事件 ID、依赖、权限版本和完整操作数据。
2. 本地投影：当前账单、冲突、债务分录、已确认收付和结算义务。
3. 传输封装：压缩、加密、分片、密文对象 ID；可随通道改变。

去重依据稳定业务事件 ID，不能只依赖密文哈希。相同事件被重新加密或由多个通道送达，仍只生效一次。

### 5.3 一致性承诺

相同已验证事件集合、依赖完整性、权限政策版本、汇率、分摊及结算算法版本，必须生成相同结果。离线成员可能只有旧视图；所谓“统一结算”是对同一快照的统一，不是任何时刻都瞬时一致。

## 6. 信息架构与核心流程

### 6.1 主要页面与当前入口

正式版本主导航为“账单 / 结算与收付 / 同步与伙伴”。

### 6.2 离线记账流程

打开本地群组 → 填写账单 → 校验金额与权限 → 原子保存签名事件及本地投影 → 显示“已保存到本机” → 各同步通道独立补传。

保存成功不能等待发现设备、WebDAV、在线时间校准、汇率服务或链节点。未联网时仍允许基于现有权限版本提出操作，但其最终可接受性由权限撤销规则处理。

### 6.3 导入流程

读取包 → 校验协议/大小 → 解密及安全解压 → 校验签名、依赖、权限和金额 → 分类新增/重复/冲突/待授权/待升级 → 展示结果 → 原子导入。

对于完整性失败的包不得部分标记成功；采用独立验证分包时，仅已完整验证的分包可提交，并准确显示剩余范围。

### 6.4 无示例首用与多账本

首次启动 → 创建出行账本或加入已有账本。创建必填“出行名称、本人昵称”，伙伴可每行一位或跳过。只建立本人 Owner 身份和创世政策，不填写酒店/晚餐等示例账或假设 FX。空账本给出“记第一笔”，后续从“同步与伙伴”管理伙伴。

同一安装可拥有多个出行账本。成员稳定 ID、事件、分类、汇率、结算、群密钥和同步队列按 group_id 隔离；切换只换账本上下文，不换成其他人的签名身份。旧页面提交和错误群包必须拒绝。旧数据库升级登记为旧账本，保留原账目/本机分类，不清表；由于旧版有代造演示身份，旧账本不能据此给别人认领。

### 6.5 自定义分类与开发者工具

分类支持单选/再次取消、Emoji 图标与新增；由有 BillCreate 能力的成员提交 CategoryUpsert 签名事件，随当前账本事件包传递。当前按 trim 后精确名称去重，不按不同账本合并。目标是新增并集、删除具有明确因果语义、历史账目不丢；现有序号排序删除并非完整 observed-remove CRDT，见第 27 节。

开发者台必须仅存在于测试构建：SBILL_TEST_TOOLS 默认关闭，Dart 和 Android 共同启用，测试包 com.sbill.app.testing 与普通包 com.sbill.app 隔离。四个测试身份持有自己的私钥，通过真实申请/批准加入同一空账本，不伪造签名、不绕过权限、不自动填账。状态/日志不记录私钥、密钥、加入包或参数；同机包交换必须说明不是网络直连。

## 8. 群组、身份与权限

### 8.1 身份与邀请

群组可离线创建，不强制手机号、邮箱或云账号。成员公钥通过邀请绑定到稳定身份，面对面可核对短身份摘要。邀请可包含接收方加密后的群组密钥和已签名政策，不能把长期密钥明文放在公开链接或留存目录中。

未安装 App 的参与人仍可被记录为付款人/承担人。线下确认或代理记录必须明确标记，不能显示“本人已签名”。默认正式共同确认要求受影响参与人具有可验证身份；代理确认是需另行明确授权的治理扩展，初始关闭。

### 8.1.1 当前离线认领实现

主人添加待认领伙伴并交付账本编号/伙伴编号 → 对方自己安装的 App 生成含公钥、设备标识、目标和 nonce 的签名申请 → 主人验签并通过可信渠道核对指纹 → 主人签名政策绑定该稳定 participantId → 生成随机高熵独立访问密钥加密的加入包 → 对方分别接收包和访问密钥，解密、验事件和本机公钥后加入。这个加入密钥不是弱用户口令，也不是已经实现的公钥 ECDH 密钥交换。

导出不包含对方签名私钥；另一公钥不能再认领已绑定伙伴。群密钥随加密加入包交付，包和访问密钥合用可读取账本，不能公开同发。认领后继承原 participantId 的历史付款/承担；未认领不能代签共同确认。当前主人可移出伙伴但不物理删除历史；成员自助退出、主人移交、换机多设备与未来群密钥轮换仍未完成。

### 8.2 默认权限矩阵

| 操作 | 账本主人 | 财务管理员 | 普通成员 | 只读成员 |
|---|---|---|---|---|
| 查看/生成本地预览/导入导出当前账本 | 是 | 是 | 是 | 是 |
| 新增/改本人账目、本人声明还款 | 是 | 是 | 是 | 否 |
| 改任意账目/解决冲突/作废 | 是 | 当前默认是 | 仅自己的常规修订/作废由核心校验 | 否 |
| 发布正式结算/提交重组 | 是 | 当前默认是 | 否（可本地预览） | 否 |
| 管理成员/批准认领/政策更新 | 是 | 否 | 否 | 否 |
| 本人签名批准/本人收款确认 | 有权且受影响时 | 有权且受影响时 | 有权且受影响时 | 当前禁止，导致受影响只读参与人的结算阻塞，尚需治理规则 |
| 代别人签名/虚构确认 | 否 | 否 | 否 | 否 |

本矩阵同时标注当前实现与未解决问题，不是用“排除只读签名”降低全体受影响人确认的原要求。原 V1.0 对财务作废/发布写“可授权”，当前默认角色已有该能力；可配置细粒度授权界面仍需补。



具体能力如 bill.create、bill.edit.own、bill.edit.any、bill.void、conflict.resolve、settlement.publish、member.manage 应独立建模，不能只在界面隐藏按钮。

### 8.3 权限政策与离线撤权

群主维护有序签名政策链；多个财务编辑可在有效授权下修改账单，不要求群主在线批准每笔编辑。操作引用授权政策版本，所有接收设备本地验证。

撤权政策应包含可接受旧操作的因果范围/检查点。已共同确认的旧操作保留；不在接受范围内、基于过期权限的未确认操作进入“待重新授权”，不能靠手机时间声称发生在撤权之前。

角色变化和密钥轮换只影响后续权限与机密性，无法收回对方此前下载的明文。发现政策链分叉应显示治理冲突，暂停正式结算，不能以“时间最新”自动选一支。

## 9. 金额、币种、付款与承担

### 9.1 金额模型

金额以该币种最小单位整数保存。币种目录保存代码和小数位并随业务版本冻结，例如 CNY/USD 为 2 位、JPY 为 0 位、KWD 为 3 位。不得用二进制浮点数累计金额或比较平衡。

每条金额必须在支持范围内；汇总与汇率乘除须检测溢出或采用足够精度整数。界面显示小数和千分位不影响原始数据。

### 9.2 账单平衡约束

每个账单记账币种下：付款合计 = 承担合计 = 账单总额。付款人可以不承担消费；记录人可以既不付款也不承担。默认金额非负，退款/冲正用明确操作类型表达，不能混入含义不明的负数。

账单不平衡时禁止保存为有效财务修订；可保存本地未签名草稿。比例合计、权重、币种精度和参与人引用必须可验证。

### 9.3 分摊

支持平均、指定金额、比例、权重、部分参与。按整数最小单位分配，先计算精确份额，再按最大余数分配尾差；余数相同按稳定 participantId 排序。最终每人的承担额和整体总额必须一致。

例如 100 分三人平均分摊，结果为 34、33、33 分；谁得到 34 分由稳定规则决定，并可在界面解释，不能因平台或成员显示顺序改变。

### 9.4 不同账单不同币种

各笔账单保留其记账币种。未正式合并结算前，币种债务独立存在，不能直接把 100 美元与 200 元相加。

### 9.5 同账单混合付款币种

推荐 P0 采用一个账单记账币种，同时记录每条付款的实际币种、实际金额、冻结汇率及折合记账金额。例如 1,000 元账单，A 实付 60 美元按约定折为 420 元，B 实付 580 元。

默认债务以账单记账币种核算，实际银行卡扣款币种作为保留信息。若需原币归还垫付人，P1 将账单显式拆成多币种债务分录；“按币种”指债务分录币种，不是任意付款备注币种。

账单汇率与结算汇率分开保存。数学取整尾差按固定规则调整并展示；无法由取整解释的差额须补充费用、汇率或付款信息，不能偷偷改动某人的金额让校验通过。

### 9.6 汇率记录

汇率包含基准/目标币种、整数分子/分母、来源、适用范围和确认版本。换算必须考虑两币种最小单位尺度，不得把“单位货币汇率”直接乘到不同尺度整数上。

MVP 支持手工冻结汇率，联网行情只是后续可选辅助。正式结算冻结汇率，后续市场变化不重估已确认债务。

### 9.7 当前外币编辑的已知缺口

Rust FxRateSpec 使用整数分子/分母并处理币种小数位，但 Flutter 外币付款编辑仍把已有原币金额统一 /100 显示，保存分母固定为 1，自动折算为 originalMinor × 整数分子。这在 JPY/KWD 等不同尺度或分数汇率下不正确，不能因 CNY/USD 7:1 样例通过而认定 AC-E07/E08 全部通过。目标仍是第 9.5/9.6 节的有理汇率与尺度约束，需修复而不是删掉要求。

## 10. 账单修订、作废与冲突

### 10.1 原子财务修订

创建、修改、作废和冲突解决均生成不可变事件。财务修订包含完整的金额、付款、承担和汇率关系；修改后全部重新校验。

管理员修改别人账单时，新事件由管理员签名、引用旧版本并记录原因。原作者签名不变；详情展示原记录人、各修订作者及修改前后差异。

### 10.2 并发分支

A/B 同时基于 V1 提交 V2a/V2b 时保留两支。对金额、付款、承担、币种等不得用最后写入覆盖，也不得逐字段合并成没人提交过的财务对象。

明确展示冲突范围。具有 conflict.resolve 权限的成员提交引用两支的新完整修订。所有设备收到同一事件集合后应看到相同冲突或解决结果。

备注等非金融字段可以单独支持自动合并，但不得借此改变财务签名含义。已知未解决财务冲突默认阻止相关债务进入正式结算。

### 10.3 已纳入正式结算的账单

已确认结算快照仍引用原修订。后续新修订不能改写旧快照或撤销已发生还款；相对该已确认修订生成差额调整，进入新一期债务。

已结算后作废也是差额/冲正，不物理删除记录。可能产生退回建议，但作废本身不证明商家退款或朋友已退钱。

## 11. 真实还款与确认

### 11.1 状态

还款记录至少包括：付款方已声明、等待收款方确认、双方已确认、存在争议、已由纠正事件调整。凭据可作为附件保留，不代替确认。

付款人和收款人对同一 paymentId、金额、币种及义务分配确认。管理员编辑账单权限不能自动代收款人签名确认到账。

### 11.2 入账规则

默认只有双方确认的还款进入正式财务余额；单方声明显示待确认，不自动让收款人“已收到”。草稿可以预览预计余额，但须与正式余额分开。

部分还款降低相应未付义务。已确认超额付款不得截断或丢弃；明确形成反向余额/退款或预付款，并由双方确认其用途。

金额相同、日期相近只提示可能重复，不能据此删除真实的两笔付款。技术去重按 paymentId/事件 ID；可选外部交易参考用于辅助识别，不假装已联通银行。

### 11.3 迟到还款

若还款引用已经重组的旧义务，保留该事实并标记“待映射”。相关当事人/授权人员明确映射到当前义务或预付款后，仅抵扣一次；禁止既抵旧义务又抵新义务。

待确认、争议及待映射收付默认阻止相关范围的下一次正式结算。不能为了结算顺畅忽略实际已经发生但尚未映射的付款。

### 11.4 当前还款闭环的不足

已接通本人声明和收款人确认。Rust 也有 Disputed/PendingMapping 等模型及迟到映射能力，但正式 App 命令白名单和界面未开放争议/纠正/映射流程；通用还款对话框也尚未覆盖所有状态。提出结算当前检查财务/政策/提交冲突和 PendingMapping，未完整检查等待确认或争议付款。第 11.3 节“相关范围阻断”继续作为未完成 P0 要求保留。

## 12. 结算模式与计算规则

### 12.1 四种模式

| 模式 | 债务币种 | 债务关系 |
| --- | --- | --- |
| 按币种 + 一对一 | 原债务币种独立核算 | 保留债权债务关系，同一对双向可抵消 |
| 按币种 + 最少/优化次数 | 原债务币种独立核算 | 每币种分别优化，不跨币种抵消 |
| 合并币种 + 一对一 | 转成选定的一种结算币种 | 同一对可跨币种折算抵消，不经过第三人重排 |
| 合并币种 + 最少/优化次数 | 转成选定的一种结算币种 | 按全组净余额重排收付 |

“一对一”不是每次转账人数的区别，而是是否保留原始债务关系。最少次数模式中的每次支付仍是一人转给另一人。

切换模式默认只改变本地预览，不改变其他成员的正式方案。正式发布必须明确币种、汇率、模式、算法及来源范围。

### 12.2 余额约束

在尚未重分类/重组的账务范围，成员余额 = 垫付 − 承担 + 已确认付出的还款 − 已确认收到的还款。正数表示应收，负数表示应付。

存在正式换币或债务重组后，还需加入对应的账务重分类分录。各币种余额总和必须为零。换币和重组不等于已支付，不能让未付义务消失。

### 12.3 多付款人的债权归因

默认按付款占比分配承担人的份额，形成付款人 × 承担人的归因矩阵；支持后续显式指定。矩阵行合计等于每个付款额，列合计等于每个承担额；本人到本人不产生转账义务。

归因取整须同时满足行、列边际金额。不能仅对每个承担人独立四舍五入而让某个付款人少收。生成结果或可复现规则版本必须随账单保存。

同一对成员的双向债务可以抵消。一对一模式不通过第三人替换债权人，即使某个整体净欠款成员也可能先从另一人收钱。

### 12.4 合并币种

使用冻结结算汇率，对约定的原币债务边换算一次，在收、付两侧记同一个整数值。原始金额保留，尾差采用固定且可解释的规则。相同汇率、边集合和规则必须得到相同余额，不允许分别四舍五入每人余额导致合计非零。

正式换币是债务计价方式改变，需要快照确认/提交；不改写消费发生时的原币账单，也不构成真实外汇兑换。

### 12.5 支付次数优化

优化目标为满足结算范围全部余额所需的非零转账次数，默认允许任意净欠款人向任意净应收人支付，无额外禁转约束。额外关系限制应作为单独模式，不沿用无约束最优声明。

一般最少次数问题是组合优化问题，简单贪心不能保证最优。推荐对非零余额成员不超过 12 人的常见小组尝试精确搜索；规模更大或确定性搜索预算耗尽时提供有效优化方案，并显示“未证明最优”。

多个最优解使用稳定成员 ID、规范化转账列表和固定并列规则选择。不可用各手机“运行一秒即停止”的墙钟时间决定统一结果。较大求解任务在后台计算，不阻塞编辑界面。

显示状态：已证明最少次数、优化方案未证明最优、不可计算（数据冲突/汇率缺失/版本不支持）。不得把后两者包装为绝对最少。

### 12.6 四人双币种示例

酒店 1,000 元：A 付 600、B 付 400，A/B/C/D 各承担 250。餐厅 100 美元：C 付款，四人各承担 25 美元。示例结算汇率为 1 美元 = 7 元，不是市场报价。

| 成员 | 人民币余额 | 美元余额 | 合并后人民币余额 |
| --- | --- | --- | --- |
| A | +350 | −25 | +175 |
| B | +150 | −25 | −25 |
| C | −250 | +75 | +275 |
| D | −250 | −25 | −425 |

默认按付款占比归因、同一对抵消后：

| 结算模式 | 转账次数 | 说明 |
| --- | --- | --- |
| 按币种 + 一对一 | 8 | 人民币 5 次，美元 3 次 |
| 按币种 + 最少次数 | 6 | 人民币 3 次，美元 3 次 |
| 合并币种 + 一对一 | 6 | 保留并折算各对债务 |
| 合并币种 + 最少次数 | 3 | 全组净余额优化 |

合并币种最少次数方案：B → A 25 元；D → A 150 元；D → C 275 元。合并一对一方案：B → A 50；A → C 25；D → A 150；B → C 75；D → B 100；D → C 175，均为人民币。

以上样例现已在核心/FFI 回归中断言余额、8/6/6/3 笔数和正式义务流程。它仅是测试夹具/数学说明，不会填充到正式新账本，也不等于真实设备验收。当前 UI 初始选择合并 CNY + 最少次数，其他本地模式可切换；原“默认按币种一对一”是早期推荐而非已兑现的配置。

## 13. 统一快照、共同确认与结算义务

### 13.1 实时预览与正式快照

预览基于本机已知数据，显示同步范围、冲突、待确认付款及汇率。正式快照冻结：纳入账单修订/调整、已确认还款、未清债务范围、政策版本、汇率、模式、算法、余额及具体方案。

快照哈希使用规范编码计算，确认者签同一哈希。确认前展示足够信息，不能仅让用户签不可读的二进制包。

### 13.2 发布与确认状态

区分本地预览、方案已提出、管理员已发布、共同确认中、共同确认完成、已正式提交、部分已还、全部已还、存在争议。

共同确认范围是债权债务被改变的所有参与人，不只是非零净余额成员。默认需要其可验证签名；管理员发布不能显示成全体同意。身份缺失/代理确认规则见第 8 节。

### 13.3 必须明确债务重组

合并币种和最少次数方案不能只是一张转账建议表。正式提交须记录“哪些旧未清债务被纳入，哪些新结算义务取代它们”。

原因：简化方案可能让原本欠 B 的 C 直接付给 A；合并币种可能让美元欠款以人民币履行。若只记录实际转账而保留全部旧债务边，切回一对一或原币视图会出现残余债务或零余额环。

正式提交产生可审计的重组/换币分录及新 obligationId。旧账单不删除，旧义务标记已转入本期，新增未付义务逐笔随真实还款减少。提交不会自动标记实际已付款。

### 13.4 避免重复重组

MVP 每群一个获授权结算提交协调者，维护带前驱的正式提交链；任何成员仍可提出预览方案。提交引用准确来源范围和已确认状态，只能消费该范围一次。

存在不同快照同时试图重组相同债务、提交链分叉或来源范围不一致时，进入冲突并暂停再次正式提交，不以最新时间覆盖。

### 13.5 后续变化

迟到账单未纳入旧快照，进入新一期；已结算账单修改生成相对已纳入修订的差额，而非再次算整张账。已发生还款永远保留。旧义务上的迟到付款按第 11 节处理。

已正式合并币种的范围在原币视图显示历史来源及“已转为本期结算币种”，不能重新要求原币支付。全部新义务履行后，切换任何模式都不应复活该范围旧欠款。

### 13.6 当前结算限制

合并币种界面固定 CNY，任意结算目标币种选择仍需实现。受影响只读成员可以承担财务，但当前核心禁止其签名批准/确认，与“所有受影响参与人本人确认”的要求形成阻塞。不得通过代签、静默剔除其签名或以测试台切换绕过解决；需要独立确认能力或明确的合法治理规则，并补验收。

待重授权/政策分叉/提交分叉的处理、完整范围展示和多设备并发提交仍未形成完整产品闭环。基础快照/重组通过不等于本节所有异常规则已通过。

## 14. 通用同步协议与状态

### 14.1 共用处理管线

所有通道使用同一业务导入器，支持幂等、依赖补齐、验证、原子落盘和结果摘要。来自普通成员的有效中转事件保留原作者签名，不把中转者当成业务作者。

优先传成员/权限依赖、财务事件、快照与确认，附件另行排队。缺少依赖的事件可以安全留存为待补齐，不得先算入余额。

当前差距：正式文件导出取当前账本全部事件，没有给用户的对端摘要请求/增量选择；导入是逐事件事务和摘要，而非整包/整个工作区原子提交。只显示新增/重复/拒绝等摘要，待依赖/待授权/待升级范围不完整。下述真正增量、确认、独立重试与整包原子要求继续保留为待完成。

### 14.2 真正增量

设备交换已验证的日志进度、头摘要和缺口；连续进度不是收到的最大序号。发生中间缺口时必须补齐，不得因为已收到序号 50 就误认为 1–49 都完整。

同一设备日志分叉须保留并报告。未知事件/算法版本提示升级，不能按默认字段解释；仅留存不代表已理解并应用。

### 14.3 状态文案

- 已保存到本机：本机持久化完成。
- 已发送：传输层发送，不代表接收方已入账。
- 已同步给成员：对方已验证并持久化相应事件范围。
- 已上传 WebDAV：留存对象已上传，不代表任何成员已读。
- 待依赖/待授权/冲突/待升级：不能进入相关正式财务投影。
- 已共同确认：指定快照达到确认规则，不代表钱已还。

各通道并行独立重试。局域网已成功也应继续补传 WebDAV，以服务离线成员；某通道失败不能阻塞本地保存或其他通道。

## 15. 局域网主同步与弱网策略

**当前未接通真实 LAN。**固定 IP 发现 DTO、组播锁和进程内 sync_lan_with_peer 不是实际发现/socket/握手。以下仍是目标，不能把模拟新增事件或 AP 隔离开关断言当成真机网络验收。

### 15.1 无公网发现和连接

使用局域网 mDNS/Bonjour 等发现，配合扫码交换连接信息的手动兜底。稳定公钥身份与易变 IP/端口分离，地址变化后重新发现。

不能用“能否访问互联网”决定 App 是否能同步。分别判断本地接口、成员路径和 WebDAV 可达性。Android/iOS 均处理本地网络权限；必要时明确选择局域网接口，避免误走移动网络。

同 Wi-Fi 不保证可互通，酒店 AP 隔离时提示原因，允许使用可互通的热点/路由器或文件/光学通道。热点可能无需公网，但设备与系统条件需验证。

### 15.2 弱网可靠性

先落盘后联网，批量传缺失事件；允许重发，按事件 ID 去重。接收方验证并落盘后才确认业务接收。断线重连核对事件范围，不相信“之前调用成功”即可。

重试采用有上限退避和抖动；连接失败不持续高频扫描。前台主动同步优先，电量低/后台减少发现频率。附件单独分块校验补传，不阻塞账单。

### 15.3 移动后台边界

iOS 普通记账 App 不能无限期保持后台 P2P socket。Android 前台服务也受权限、系统及厂商功耗限制。产品承诺打开 App 时自动补齐，后台尽力，不承诺实时全局一致。

APNs/Android 推送不进入离线正确性前提；若以后增加提醒，应作为明确的外部服务依赖，而非假装无服务器。

### 15.4 其他附近技术

BLE、Wi-Fi Aware 作为增强适配，不是 MVP 唯一链路。iOS 26 Wi-Fi Aware 提供非 Apple 设备互通路径，但 Android 硬件、固件和配对能力仍需兼容验证。传统 Apple 专有点对点 Wi-Fi 不能作为通用 Android/iOS 协议。

## 16. WebDAV 加密异步留存

**当前未接通 HTTP WebDAV。**只有 WebDavRemoteStore 接口、InMemoryWebDavStore、出箱和模拟可达性；以下真实认证、证书校验、上传/拉取、退避和节点迁移仍是需求。

### 16.1 可用节点与网络边界

支持 NAS、Nextcloud、符合要求的 WebDAV 网盘。它是文件服务，不是无服务器；客户端仍持有业务权威数据。配置为可选，不配置也能本地、局域网和手动交换。

A/B 非同时在线且无公网时，必须有双方可访问、常开且位于可达局域网的留存节点。家中 NAS 若没有任何连接路径，旅行途中无法访问。只配置公网 WebDAV 时，断公网仍可局域网同步，上传留在队列。

也可借 C 的手机随实际接触转递事件，但不保证及时送达。

### 16.2 存储与并发

远端按不含人名的群组标识划分目录，保存不可变密文事件对象及附件。可选的每设备索引是提示，不是事实来源。不能让所有人覆盖同一个 ledger.json 或依赖文件修改时间认定最新账单。

使用目录枚举/对象读取/幂等写入等能力；条件请求与 ETag 按服务端实际支持使用，不作为正确性的唯一前提。下载后校验内容、解密和验签。上传中断、重复对象、陈旧索引或服务端改写必须可恢复。

默认不由客户端删除远端历史。历史压缩/回收需另行设计检查点、离线成员恢复及备份规则。

### 16.3 凭据与节点配置

使用 App 专用账号/目录，优先每成员独立低权限凭据，禁止共享 NAS 主账号。凭据存本机安全存储，不写日志/业务导出。HTTPS 证书必须正确验证，不因内网而关闭验证。

可为同一仓库配置局域网/远程入口，明确仓库标识；不能只凭路径同名认定同一仓库。状态分别显示可达性和未上传/未拉取数量。

### 16.4 安全与失败

WebDAV 运营者可能删除、回滚或扣留对象。签名和本机检查点可发现部分篡改/回滚，但冷启动设备不能凭空知道被隐藏的最新事件。恢复需要可信成员/备份提供检查点。

保留手机副本及独立备份。节点停服时本机可读写，未传播数据仍显示未同步；切换节点不自动清空已知账本。

## 17. 文件、系统互传、文本与数据图片

### 17.1 同步文件为主

FR-SYNC-03 导出实际数据包，而非下载链接。推荐扩展名 .tripdelta；如厂商工具对自定义类型支持不佳，可采用标准文件外壳。ZIP 外壳不替代应用层认证加密。

iOS 接入系统分享、文件选择和“打开/分享给 App”；Android 接入分享/查看 Intent 与授权文件 URI。只要求使用通用文件入口，不假设能直接控制厂商私有协议或后台自动收发。

对方导入显示新增/重复/冲突/未授权范围。相同包反复传不重复计费、不重复入账。发送成功不能代替业务导入确认，可生成小确认码/文件。

### 17.2 iPhone 与小米互通条件

已核实官方文档：小米互联服务可在兼容 HyperOS 2+ 设备与 Apple 设备之间传图片/文件；iPhone 安装并打开应用、启用蓝牙，按文档使用同一局域网/热点。安装、登录、更新等准备应提前完成。

部分具备条件的小米设备支持 Quick Share 与 AirDrop 直接互通，依机型、地区和 Google 服务等条件；不能保证任意国行设备可用。某些不支持机型的 Quick Share 二维码替代路径会上传云端，需要双方公网，不属于本产品离线通道。

测试必须关闭公网和双方蜂窝数据、保留所需无线链路，完成双向原文件导入。当前仅验证了文档条件，尚未进行具体机型测试。

### 17.3 编码文本

适合邀请和小增量。包含明确协议前缀、完整性和加密数据；不得默默接受截断内容。Base64 约增加三分之一体积，长文本的截断/格式化和剪贴板隐私风险需提示，不作为大包首选。

### 17.4 静态二维码与图片

普通二维码图片内嵌实际小包，不是公网 URL。适合小邀请/少量更新；不能默认一张普通 QR 装下几十 KiB。

P2 数据 PNG 有两类：画面编码数据、或 PNG 自定义数据块承载加密包。App 接收原 PNG 后直接解析，不需要摄像头再次拍屏，也不依赖 OCR。

RGB 像素字节空间只代表原图解析容量，不代表相机能恢复每个像素值。截图、缩放、JPEG 转换、渲染重存或元数据清理可能破坏载荷。因此 PNG 通道要求原文件保真，失败明确提示发送原文件；不能作为唯一通道。

画面封面默认不泄露账单金额、人名和长期密钥，只展示必要的包类型、版本、数量及校验摘要。提供原始同步文件兜底。

## 18. 完全无无线连接的光学通道

**当前只是 JSON/XOR 分片恢复与演示。**画面是仿二维码，没有标准 QR/Multipart UR 编码或相机解析；也没有双向摘要请求/确认和持久接收缓存。以下光学场景均未完成真实产品/物理设备验收。

### 18.1 协议与交互

FR-SYNC-04 采用动态二维码/Multipart UR 与喷泉码等成熟机制；不优先自研整屏彩色光学通信。所有识别、编解码、解压、加解密均随 App 本地提供，首次离线使用不能等待下载识别模型。

B 展示已有数据摘要请求 → A 扫描并选择缺失事件 → A 展示动态 QR → B 持续接收、恢复、验签并持久化 → B 返回接收确认；双方都有新增时换方向再传。

喷泉码允许中途开始、容忍漏帧。接收进度缓存绑定固定传输包，暂时失焦后可继续；新包不得混用旧分片。QR 内部纠错与整帧丢失容错分别处理。

### 18.2 建议起步参数

每帧净数据 250–500 字节、动画 3–6 帧/秒作为初始调优范围；正文/编码/分片开销必须计入生成器容量，不等于每帧 QR 文本长度。

净有效吞吐预算为 0.5–2 KiB/s，未在双手机实测。屏幕/摄像头帧率不等于有效成功解码帧数，光照、对焦、反光与滚动快门影响较大。

提供慢速/手动翻页模式，背景保持稳定，不做整屏明暗强频闪。优先降低密度和速率让低端设备成功，而非强行提高帧率。

本次用合成 JSON 事件、简短备注、固定分摊、随机 ID/等长随机签名字段及 zlib 批量压缩计算大小；未传照片。外层开销按 96 字节估计，不是正式协议实测。

| --- | --- | --- | --- |
| 10 | 14.2 KiB | 3.2 KiB | 约 2–7 秒 |
| 50 | 72.5 KiB | 11.5 KiB | 约 6–24 秒 |
| 100 | 145.3 KiB | 21.9 KiB | 约 11–44 秒 |
| 200 | 291.2 KiB | 42.5 KiB | 约 22–86 秒 |

单次完整修订样本约 0.9–1.2 KB。真实复杂备注/分摊应留至少两倍余量；100 个事件按 40–80 KiB 规划，纯传输约 20–160 秒，另加对准/请求/确认时间。

已加密 WebDAV 对象直接拼接基本无法获得批量压缩收益。光学通道先提取稳定签名业务事件，批量压缩再加密；仍按原事件 ID 去重。

一张 1 MiB 照片按预算约需 8–34 分钟，不作为默认光学内容。账单、权限、还款和快照先传，照片仅传引用，局域网/WebDAV 可用后再补齐。

### 18.4 安全导入与限制

完整验证后才入账，CRC 不代替认证加密或作者签名。限制包大小、分片数量、解码内存、解压体积和解析深度；超限提示切换文件通道，不允许无限分配资源。

二维码只证明接收了字节，不证明消费真实性或对方有编辑权限。旁观者可拍下画面，因此财务载荷必须加密；邀请密钥保护见第 8 节。

## 19. 附件、备份与恢复

当前只有整块加密附件/缺失报告和个人口令备份原型，正式账目 FFI 写空附件列表，没有附件或备份/换机用户入口。备份原型的单次 BLAKE3 口令派生和确定性盐不满足安全 KDF 要求；普通私有 SQLite 存种子/群密钥不等于 Keystore/Keychain 安全存储。以下需求不能标为已经完成。

### 19.1 附件

照片单独加密、内容寻址和分块校验。账单可引用尚未传到本机的附件，明确“附件待同步”，不因附件失败阻止有效账单入账或伪装附件已存在。

删除可见附件引用不保证远端或旧设备的副本被删除。默认不在导出封面、日志和对象文件名中包含敏感内容。

### 19.2 账本备份不等于密钥备份

同步包包含业务事件，不默认包含成员签名私钥。密钥备份必须使用该成员独立恢复秘密/口令保护，不能只用全群持有的群密钥，否则别人可能恢复其签名身份。

导出与恢复须分别告知：数据完整度、附件缺失、当前群密钥是否可用、签名身份是否恢复、是否需要群主授权新设备。

换机生成新设备身份并完成授权后保留原成员历史，不盲目复用旧日志序列。群主密钥和备份都丢失时不能宣称自动恢复原授权，可提供带明确历史边界的新群组迁移流程。

## 20. 安全、隐私与信任边界

- 使用成熟库的认证加密与数字签名，正确管理 nonce、密钥版本和规范编码，不自创密码算法。
- 群密钥保护内容；作者签名保护作者归属。仅持群密钥不能伪造他人有效签名。
- 密钥/留存凭据使用平台安全存储；导出和日志不得泄露明文私钥、应用密码或恢复秘密。
- 退出成员撤销访问凭据，轮换未来群密钥；历史副本和旧已确认记录不因撤权消失。
- 输入来自 LAN/WebDAV/文件/图片/QR 均视为不可信，统一限额、验签和授权。
- 不按不可信文件路径解压到任意位置；标准外壳需防路径穿越、解压炸弹和危险文件类型执行。
- 本地确认后才开放群组数据给新成员，不能仅因同网或二维码出现就授予角色。
- 应显示权限/提交链分叉、旧快照回放和缺依赖，不能用最新时间或随机选支掩盖。
- 普通分析日志默认仅记录非敏感技术摘要；任何遥测上传应明确选择，不成为离线可用前提。
- 公开链不证明线下消费或银行到账，也不保证数据留存；不把可选锚定描述成真实性验证。

MVP 假设群主/治理授权存在可接受的信任基础。可检测双重签署等冲突，但不提供恶意多数或恶意群主下的金融共识保证。

| 局域网同步 | 连接建立后，10 个无附件常规事件目标 3 秒内完成验证落盘；发现/权限耗时另计 |

更大包通过分页/分包或文件通道处理，不因越界静默丢事件。附件另设限额，不混入上述无附件基准。

### 25.2 估算边界

本文数据大小来自合成事件的序列化/压缩模型，签名字段为等长随机字节，外层开销为估计；不包含照片，不表示正式协议已定。0.5–2 KiB/s 是光学工程预算，不是引用文档中的测速值。数学结算示例可以复算；应用、无线互通和摄像头吞吐仍需实现后测试。

KiB = 1,024 字节；MB/MiB 出现时按明确单位解释。普通 QR 理论最大容量不能直接等同实用扫码净载荷，也不能等同数据 PNG 原文件容量。

### 25.3 术语

- 无公网：没有互联网，但局域网、热点或附近无线链路可能可用。
- 完全无无线连接：不能使用 Wi-Fi、蜂窝或蓝牙；屏幕/摄像头仍可作为光学通道。
- 本地优先：本机数据与操作可用性优先，不等同没有任何基础设施。
- 异步留存：发送方上传后离线，接收方稍后从共同可达节点获取。
- 签名事件：证明某身份提交了特定操作，不证明线下消费或到账事实。
- 修订：对账单提出新版本，旧记录仍存在。
- 正式快照：冻结数据范围与规则、可共同确认的结算依据。
- 结算义务：正式方案生成的未付债务，不是已发生付款。
- 债务重组：在确认范围内用新义务取代旧未清关系，保留来源与审计。
- 币种重分类：经确认改变债务计价币种，不等同真实换汇或已经清偿。
- 喷泉码：通过冗余编码容忍部分帧缺失，适合动态 QR 的不可靠光学接收。
